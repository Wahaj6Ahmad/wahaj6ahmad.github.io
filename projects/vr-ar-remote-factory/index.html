VR/AR Remote Factory Support

A mixed reality pipeline for FrieslandCampina: annotate defects in VR, see guidance on the real product in AR

The big idea: VR for precise annotation, AR for in-context feedback on the real object.

This project was built for FrieslandCampina. The problem was very practical: packaging developers (based in the Netherlands) cannot always be physically present during trial sessions at the factory site in Indonesia, and regular video calls make it hard to point out defects precisely on a real product. :contentReference[oaicite:0]{index=0}

So we designed a mixed reality workflow: a quality manager inspects a highly accurate 3D scanned model in VR, draws directly on it, and the on-site team sees those annotations overlaid on the real product through an AR camera or AR glasses. :contentReference[oaicite:1]{index=1}

Client: FrieslandCampina.

Prototyping the VR annotation experience

This project is where my UI/UX “overthinking” became useful. I had to design an annotation tool that feels obvious in VR: simple, minimal, and fast to use, without turning the user’s left hand into a menu jungle. :contentReference[oaicite:2]{index=2}

What the system does

The core workflow is a two-part loop:

  • VR side (Netherlands): inspect a 3D model of the product in a factory-like VR environment, then draw annotations directly on the model for precise defect communication. :contentReference[oaicite:3]{index=3}
  • AR side (Indonesia): track the real product using markers and overlay the latest VR annotations onto the corresponding physical surface in the camera view. :contentReference[oaicite:4]{index=4}
Technical details

Architecture (VR → server → AR)

The system connects a VR annotation app (Unity) with an AR feedback app (Python/OpenCV) through a server, so the latest annotations can be transmitted and shown in-context on the real object. :contentReference[oaicite:5]{index=5}

Full process of the annotation feedback system.

VR implementation

The VR prototype was built in Unity (C#) using OpenXR for integration with the Oculus Quest Pro. A key design decision was placing the drawing palette on the user’s left hand, so color and stroke width changes stay within reach while the user keeps focus on the product. :contentReference[oaicite:6]{index=6}

VR annotation palette (color + stroke width).

AR implementation

The AR side was implemented in Python using OpenCV. For tracking we used ArUco markers (6x6_250 dictionary) placed on the product’s surfaces. The program detects the marker ID, estimates camera pose, identifies which face is visible, then transforms the matching annotation image so it “fits” onto that plane in the camera view. :contentReference[oaicite:7]{index=7}

For the demo, we generated annotation renders from multiple sides of the product every second, transmitted them, and mapped them back to the correct surface in AR. :contentReference[oaicite:8]{index=8}

We also treated security as part of “technical quality”: communication is secured via SSL/TLS, and generated content is stored temporarily and deleted when the session ends. :contentReference[oaicite:9]{index=9}

Overall AR feedback structure.

Tech used

  • Unity + C# (VR application)
  • OpenXR (Quest Pro integration)
  • Python + OpenCV (AR overlay + tracking)
  • ArUco marker tracking (6x6_250 dictionary)
  • Server bridge to transmit annotations between VR and AR
  • SSL/TLS encryption + session-based deletion of generated data
UI/UX decisions

In VR, UI mistakes are expensive. If the tool is confusing, the user can’t “power through” like they can on a laptop. So the annotation menu was designed to stay minimal (few buttons, no long text), and still support the features that matter in real work: undo/redo and erasing without hunting for it. :contentReference[oaicite:10]{index=10}

We used classic usability heuristics as guardrails (aesthetic/minimalist design, visibility of system status, user control and freedom). Concretely: the pointer changes width and color based on the selected brush, hover states give feedback, and selection is shown clearly so the user never wonders “what am I drawing with right now?” :contentReference[oaicite:11]{index=11}

Base UI color palette (checked for contrast accessibility).

Accessibility wasn’t an afterthought. We checked the palette against WCAG contrast guidance, and kept the interface readable for users with visual impairments. :contentReference[oaicite:12]{index=12}

For annotation colors, we avoided a full color wheel. Instead we used a limited set of options (enough to be expressive, not enough to be overwhelming). Six of the annotation colors were inspired by the FrieslandCampina logo so the tool feels consistent with the client’s world. :contentReference[oaicite:13]{index=13}

Annotation palette color options (simple on purpose).
Evaluations + learnings

Test plan highlights

  • Functionality: prove the full loop works (annotate in VR → see feedback in AR). :contentReference[oaicite:14]{index=14}
  • Performance constraints: we limited the demo target to a rectangular prism package shape. :contentReference[oaicite:15]{index=15}
  • Usability: two rounds of testing; we tuned overlay opacity and iterated QR/marker sizes to improve realism. :contentReference[oaicite:16]{index=16}

A big lesson for me: “it works” is not the same as “it lines up convincingly on a real object.” Most of our practical iteration was about alignment, scaling realism, and making the AR overlay feel glued to the product. :contentReference[oaicite:17]{index=17}

When a system has this many steps, testing stops being optional.
