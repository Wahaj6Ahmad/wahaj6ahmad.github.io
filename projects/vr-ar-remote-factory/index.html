VR/AR Remote Factory Support

A mixed reality pipeline for FrieslandCampina: annotate in VR, see it on the real product in AR

The big idea: VR for precise annotation, AR for in-context feedback on the real object.

This project was built for FrieslandCampina. The ask was simple to say and hard to solve: how do you feel fully “present” during a remote factory trial when the environment is noisy, the connection can be slow, and a 2D video call doesn’t give enough context to discuss a complex production line?

We focused on one concrete slice of that problem: product defect communication. Instead of trying to “point at the screen” over a shaky call, we built a workflow where a remote expert can annotate a highly accurate 3D scanned model in VR, and the on-site team can see those annotations directly overlaid on the real product in AR.

Client: FrieslandCampina.

How this helps (and why MR beats a normal call)

  • Better shared context: VR gives the remote expert a stable, inspectable view of the product in a factory-like setting.
  • Precise communication: instead of describing “that scratch near the top-left”, the expert draws on the exact surface.
  • In-place guidance: AR puts the annotation back onto the real object so the on-site team sees what to change, on the product, not on a laptop.
  • More “presence” with less noise: the key information becomes visual and spatial, not dependent on perfect audio in a loud environment.

What the system does

The core workflow is a two-part loop:

  • VR side (remote expert): inspect a 3D model in VR and draw annotations directly on the surface to mark defects precisely.
  • AR side (on-site team): track the real product using markers and overlay the latest VR annotations onto the corresponding physical faces.
Technical details

Architecture (VR → server → AR)

The VR annotation app and the AR feedback app are connected through a server so the latest annotations can be sent and shown in-context on the real object.

Full process of the annotation feedback system.

VR implementation

The VR prototype was built in Unity (C#) using OpenXR for integration with the Oculus Quest Pro. We used hand tracking and placed the drawing palette on the user’s left hand so color and stroke width changes stay within reach while the user keeps focus on the product.

For the demo pipeline, we generated renders from multiple sides of the package every second and transmitted them to the AR side, where they were mapped back to the correct surfaces.

VR annotation palette (color + stroke width), placed on the left hand.

AR implementation

The AR side was implemented in Python using OpenCV. For tracking we used ArUco markers (6x6_250 dictionary) placed on the product’s faces. The program detects marker IDs, estimates pose, identifies which face is visible, then transforms the matching annotation image so it fits the plane in the camera view with the correct perspective.

We also treated security as part of “technical quality”: session content is stored temporarily and deleted after the session, and communication is secured using SSL/TLS.

Practical learnings (the stuff you only learn after building it)

  • Alignment realism matters: “it works” is not the same as “it looks glued to the object.” We had to tune opacity and scaling to make overlays believable.
  • Tracking constraints shape the product: we scoped the demo to a rectangular prism and flat faces to keep tracking stable.
  • Synchronization is the hard part: the core challenge wasn’t drawing in VR or detecting markers in isolation, but making the whole loop feel consistent end-to-end.
Overall AR feedback structure.

Tech used

  • Unity + C# (VR application)
  • OpenXR (Quest Pro integration)
  • Oculus Quest Pro hand tracking
  • Python + OpenCV (AR overlay + tracking)
  • ArUco marker tracking (6x6_250 dictionary)
  • Server bridge to transmit annotations between VR and AR
  • SSL/TLS encryption + session-based deletion of generated data
UI/UX decisions

In VR, UI mistakes are expensive. If the tool is confusing, the user can’t “power through” like they can on a laptop. So the annotation menu was designed to stay minimal (few buttons, no long text), and still support the features that matter in real work: undo/redo and erasing without hunting for it.

We used usability heuristics as guardrails (minimalist design, visibility of system status, user control and freedom). Concretely: the pointer changes width and color based on the selected brush, hover states give feedback, and selection stays visible so the user never wonders “what am I drawing with right now?”

Base UI color palette (picked for contrast and readability).

Accessibility wasn’t an afterthought. We checked the palette against WCAG contrast guidance and kept the interface readable. For annotation colors, we avoided a full color wheel and used a limited set of options: expressive, but not overwhelming. Six of the annotation colors were inspired by the FrieslandCampina logo to keep the product visually cohesive.
