Roarbot

A door-opening robot arm built during COVID from scrap parts and spare electronics

Roarbot: the robot that exists because I refused to let a locked door win.

Roarbot was my bachelor’s capstone in Electrical Engineering (Spring 2020), built during COVID when I did not have access to the university lab. That single constraint shaped the whole project: I had to build a working robot arm using scrap material, spare parts, and whatever tools I could realistically use at home.

The goal was to design an autonomous system that can detect a lever-handle door lock and open it using a vision-guided manipulator. But the real thing I’m proud of is the engineering mindset it forced: making decisions based on reality, integrating hardware + software end-to-end, and iterating through messy tests until the system behaves.

What Roarbot does

Roarbot uses a single mobile camera to locate a door handle, estimates its 3D position, moves a 4+1 DOF manipulator to reach the lever, confirms contact, twists to unlock, and then retracts along a controlled pull to open the door.

The loop: vision → 3D location → inverse kinematics → move → contact → twist → pull open.

Doors are where robotics stops being “nice in theory”. They fight back, they misalign, and they force you to make the whole perception-to-action chain reliable.

Built from scrap (the part I want you to notice)

Because I couldn’t access the lab during COVID, I built Roarbot’s hardware using scrap material and spare parts. I didn’t treat this as a limitation. I treated it as the design brief.

The best example is the actuator choice: I repurposed car air-fresher motors. They were accessible, surprisingly strong, and had a worm-gear assembly that helped hold position under load. Even better: the motor driver was already installed on the board, which made integration simpler and faster.

Scrap air-fresher motor: worm gear assembly = high torque and hard to back-drive.
DIY feedback: a potentiometer coupled to the shaft to act like an “encoder” when real encoders weren’t available.

This is the kind of build that teaches you what “engineering” really is: not picking perfect components, but understanding what you have, extracting stable behavior out of it, and designing around the constraints.

Base mechanics and motor mounting: built to survive repeated testing, not to look pretty.

Before committing to the full build, I demonstrated the concept with a smaller prototype. It was my “prove the loop first” step: detect, reach, contact, and pull. Once that worked, scaling up felt like engineering instead of guessing. Proof-of-concept video.

Technical overview

This is the full breakdown. It’s long, but it’s the part that sells me as a builder: a working system with hardware implementation and software implementation that actually talk to each other.

Technical details (hardware + software)

Hardware implementation

  • Scrap actuation: air-fresher DC motors with worm gears + integrated driver boards.
  • Feedback: potentiometer-based position sensing attached to joints.
  • Structure: mixed material build (whatever could be sourced reliably during lockdown).
  • Contact confirmation: simple sensor/switch logic to detect when the handle is engaged.
  • Controller: Arduino-based control for joint actuation and feedback handling.
Hardware block diagram: how power, actuation, and sensing are wired into the control loop.
Electrical setup: the part that always looks simple until you have to debug it.

Software implementation (perception → 3D → control)

1) Vision (single camera)

A mobile camera provides the input stream. The frame is processed to isolate the handle region, then the handle position is extracted (centroid / region properties). The key is consistency: once the vision output is stable, the control side becomes predictable.

One frame, multiple steps: raw image → mask → cleanup → handle localization.
Input vs output: turning pixels into a target the robot can move toward.
2) 3D estimation + arm frame alignment

The 2D handle location is converted into a usable 3D target (with calibration and coordinate alignment), then translated into the arm’s working coordinates.

3) Inverse kinematics + motion control

An IK solution computes joint targets for reaching. The Arduino drives actuation while monitoring joint feedback, enforcing bounds, and keeping motion stable under load.

4) Door opening routine

The end effector approaches, confirms contact, twists the lever to unlock, then performs a controlled pull to open the door. This is where robustness matters: the sequence has to tolerate small misalignments without instantly failing.

Tech used

  • Arduino (control + feedback)
  • MATLAB (vision pipeline)
  • Single mobile camera stream (phone as camera)
  • Potentiometer-based joint feedback
  • Repurposed DC motors with worm gears + integrated drivers

Why this matters for my robotics path

Roarbot is the project I use to prove I can build robots outside ideal conditions. No lab, no perfect parts, and still a system that integrates perception, mechanics, control, and feedback.

  • Scrap-to-system engineering: I can build with constraints and still deliver working behavior.
  • Full-loop integration: vision is only useful if it drives real motion. Roarbot does that.
  • Debugging mindset: the failures are documented because they are part of the engineering story.
